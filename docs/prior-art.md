# Prior art

What already exists for talking to NovaStar hardware, and what each is worth to
a new application. All the third-party projects below are MIT-licensed; read the
provenance note at the end before vendoring any of them.

## Reverse-engineered libraries

### `sarakusha/novastar` — TypeScript, MIT

The most substantial public work by a wide margin, and the reference this
investigation leaned on hardest.

- `@novastar/codec` — the frame codec: header, addressing, additive checksum,
  chunking, response matching. Independently confirms every field this
  repository's `protocol.py` implements.
- `@novastar/net` and `@novastar/serial` — transports, including the UDP 3800
  discovery handshake with the `rqProMI:` / `rpProMI:` probe and the multicast
  group.
- `@novastar/native` — **~1,500 named register addresses** and over a thousand
  API methods, generated from decompiled NovaLCT assemblies. This is the single
  richest source of address knowledge in public, and the one with the most
  awkward provenance.
- `@novastar/screen` — a partial reimplementation of NovaLCT's screen
  configuration layer. Useful mostly as a survey of how much complexity that
  layer holds.
- `wireshark/novastar.lua` — a Wireshark dissector bound to TCP 5200/5201/5203,
  with an address-name lookup table. **Start here** when capturing a NovaLCT or
  VMP session; it turns an opaque hex stream into named register operations.

The repository also carries copies of several NovaStar protocol PDFs that are
otherwise hard to find, including the MCTRL 660 Pro and M3 documents used here.

### `@novastar-dev/coex` — TypeScript, MIT

A thin, current client for the COEX HTTP API on port 8001. Small enough to read
in one sitting and effectively a machine-readable index of the endpoint set;
useful for cross-checking the official manual against what firmware actually
serves.

### Bitfocus Companion modules — JavaScript, MIT

- `companion-module-novastar-controller` — register bus over TCP for MCTRL4K,
  VX4S, VX6S and similar. Notable detail: VX Pro-series controllers use port
  **15200** rather than 5200.
- `companion-module-novastar-coex` — HTTP API for MX40 Pro, KU20, CX80 Pro.

Both are structured as fixed command tables rather than a general register
interface, which limits them to their pre-built action lists — the design
mistake worth not repeating. Their hard-coded frames also carry stale checksums
that omit the serial-number byte; the modules recompute before sending, so the
tables must not be copied verbatim. That is pinned as a test in this repository.

### Smaller projects

- `dietervansteenwegen/Novastar_MCTRL300_basic_controller` — Python, brightness
  and test patterns over the MCTRL300's CP2102 USB-UART. A good minimal example
  of the serial path.
- `cedric-uden/Novastar-Controller` — MCTRL 660 Pro over TCP 5200, values
  obtained by Wireshark capture. Mostly of interest as a worked description of
  the capture-and-diff method.

## Official NovaStar interfaces

Worth knowing precisely, because they change how much reverse engineering is
actually required.

| Interface | Applies to | Notes |
|---|---|---|
| COEX Series Interface API | MX/CX/KU controllers | HTTP JSON on port 8001, ~90 endpoints, unauthenticated. The documented path to most VMP-like functionality. |
| COEX Central Control Protocol | MX/CX/KU controllers | The register bus, documented: TCP 5200, UDP 5201, RS232 115200. Current as of V1.5.0, 2025. |
| COEX SNMP | MX/CX/KU controllers | Published MIB for monitoring. |
| Nova Control System Protocol (M3) | Sending cards and processors generally | 71 pages, 2018. The authoritative field-by-field specification of the register bus, plus command tables for monitoring, brightness, gamma, display control, redundancy and calibration. |
| MCTRL 660 Pro / VX4S / PRO HD protocol notes | Those models | Short input-switching documents with usable hex examples. |
| Nova Mars LED SDK | Legacy | Windows DLL SDK, 2016. Superseded, but its API surface shows how NovaStar itself decomposed the domain. |

The existence of the first four is the most important finding for anyone
planning a product: for current hardware, the majority of the work sits on
documented interfaces, and the reverse-engineered material is needed mainly for
older processors and for configuration depth.

## Provenance

Every third-party project above is MIT-licensed, so the code itself is
reusable on those terms.

The exception worth thinking about is `@novastar/native`. Its address map and
API surface were generated by decompiling NovaLCT's .NET assemblies, and the
package ships those DLLs. An MIT header on generated output does not settle the
status of the original. Treating the addresses as facts to verify against your
own hardware is a materially different position from vendoring the generated
code or redistributing the binaries. If this becomes a product rather than an
experiment, that distinction deserves a deliberate decision — and legal input
rather than an engineer's guess.
